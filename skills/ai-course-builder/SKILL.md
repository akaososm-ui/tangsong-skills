# AI Course Builder

## Purpose

Turn an instructor's real experience, judgments, cases, and delivery process into a course that learners can understand, practice, submit, receive feedback on, and reuse.

This is not a one-click course generator or a slide-writing shortcut. Establish the learner result first, extract the instructor's own judgment before expanding with AI, and keep human review gates before any final delivery, visual production, or publishing step.

## When to use

- A single class, workshop, public session, or training add-on;
- A cohort, bootcamp, recorded course, or curriculum map;
- A course manual, handout, teaching script, exercise, assignment, or FAQ;
- A repeatable workflow for turning teaching records into course assets.

Do not use this skill to fabricate credentials, testimonials, learner outcomes, case studies, revenue claims, or a complete course when the source material and result boundary are missing.

## Required intake

Before designing the course, collect a course brief with:

- **Format:** single session, workshop, cohort, recorded course, or curriculum;
- **Learners:** actual audience, current stage, prerequisites, and reachable group;
- **Problem:** repeated learner pain, previous attempts, and why they did not solve it;
- **Result:** the action, artifact, decision, or workflow learners must complete;
- **Instructor:** relevant experience, judgment criteria, evidence, cases, and claims that must not be made;
- **Direction:** topic, working title, delivery context, business or learning goal, and scope;
- **Materials:** recordings, consultation notes, prior lessons, articles, learner questions, templates, or demonstrations;
- **Constraints:** duration, group size, tools, equipment, delivery mode, copyright, privacy, and accessibility needs.

Separate every input into: verified fact, observed pattern, instructor judgment, external source, or unverified hypothesis.

If the learners, problem, instructor basis, or observable result is still unclear, output an **intake brief** with missing information and confirmation questions. Do not generate a complete course plan yet. Do not fill missing tool features, prices, statistics, or platform behavior from memory.

## Core principles

1. **Define the result before the format.** Learners buy a clearer judgment, an executable method, a submitted artifact, or a concrete decision—not a number of lessons.
2. **Instructor first, AI second.** AI may organize, expand, check omissions, and draft. It must not replace the instructor's experience, cases, evidence, or key trade-offs.
3. **Validate the delivery loop.** A course is effective when learners complete the action, leave an artifact, receive feedback, and can reuse the result in a later situation.
4. **Keep provenance visible.** Mark what came from the instructor, what came from external material, and what still needs verification.
5. **Respect privacy and rights.** Anonymize learner and client information, use only authorized materials, and do not reproduce copyrighted benchmark content as course material.

## Workflow

### 0. Build the course brief

Clarify what learners must be able to do, what evidence will prove it, why this instructor can teach it, and what is outside the course boundary.

### 1. Calibrate the need and result

Test whether this is a real learner problem or only an instructor's preferred topic. Capture repeated questions, previous attempts, desired result, success evidence, unsuitable learners, and delivery limits.

Write the result as an observable statement:

> By the end of the session or program, learners can complete ______ and submit ______ as evidence.

Minimum loop for a single session:

```text
real problem -> executable path -> in-session artifact -> next action
```

Minimum loop for a curriculum:

```text
final result -> milestones -> modules -> lesson actions -> assignments/feedback -> final artifact
```

When demand or the buyer/learner group is still unclear, recommend a diagnostic, small workshop, or pilot before a large recorded course.

### 2. Map the instructor's experience

Before writing polished teaching copy, create three maps:

1. **Major modules:** the main learner problems to solve;
2. **Sub-problems:** concrete points where learners get stuck;
3. **Evidence and actions:** instructor cases, judgment criteria, demonstrations, learner exercises, and expected artifacts.

For each knowledge point, capture the situation, instructor judgment, reason for the judgment, real case, learner action, common error, and boundary.

### 3. Benchmark and fill gaps

Only after the instructor's own map is complete, review comparable courses, public content, learner language, or search terms. Extract only problem naming, sequence, result framing, case form, practice, and delivery choices.

Do not treat benchmark material as the instructor's experience. If a specialized content-analysis skill is unavailable, ask for the complete source or skip the benchmark step; do not invent or infer missing source material.

### 4. Set positioning and structure

Use this sentence as a working position:

> Help **[which learners]**, through **[which path]**, solve **[which problem]**, and complete **[which visible result]**.

Then decide the format, title, module order, content boundary, and next-step path. Do not use unsupported income, speed, employment, health, or guaranteed-result claims.

### 5. Draft the outline

Use the confirmed course brief, experience map, benchmark observations, result boundary, and constraints.

For every module, specify:

- learner problem;
- learning objective;
- instructor judgment to explain;
- learner action;
- learner artifact;
- case or demonstration;
- practice and feedback;
- condition for moving to the next module.

Order the course by learning dependency, not by the order in which the instructor remembered the topics. A longer course is not automatically a more valuable course.

### 6. Expand one segment at a time

Use this loop:

```text
instructor points -> AI expansion -> case/source check -> instructor review -> next segment
```

Process one module or knowledge point per pass. A useful unit contains: situation, judgment, method, example, learner action, common errors, check standard, summary, and next action.

If theory becomes too heavy, a case is not real, a key judgment is missing, or the language does not fit the instructor, revise that segment instead of regenerating the entire course.

### 7. Assemble the teaching package

For a single session or workshop, prepare as relevant:

- course brief and positioning;
- time plan and teaching path;
- demonstration or case script;
- live exercise and success sample;
- troubleshooting checklist;
- Q&A and escalation boundary;
- learner handout;
- post-session action and feedback channel;
- retrospective and assetization checklist.

For a curriculum, prepare:

- final result and completion artifact;
- target and unsuitable learners;
- prerequisites;
- milestones and module map;
- lesson actions and outputs;
- assignment and feedback rhythm;
- completion risks and recovery paths;
- tool, material, version, and delivery boundaries;
- final acceptance criteria;
- follow-on service or learning path;
- retrospective and update plan.

Create slides, formatted documents, or publishing assets only after the text structure has been confirmed. Use whatever document, presentation, or publishing tools are actually available in the user's environment; do not assume a particular platform.

### 8. Design delivery and feedback

A single session should normally include preparation, shared context, case or judgment, demonstration, individual or group practice, showing the result, feedback, a next action, and a feedback route.

Design what learners do, not only what the instructor says. State the success sample, common errors, troubleshooting method, what can be handled live, and what belongs in later support.

### 9. Retrospect and assetize

After delivery, separate:

1. **Facts:** what happened;
2. **Observations:** what worked or got stuck;
3. **Assets:** methods, SOPs, cases, FAQs, templates, or prompts worth preserving;
4. **Iteration:** what to remove, add, reorder, or change in format.

Only a process that has repeated and stabilized should become an automation or agent rule. Keep one-off judgments, sensitive decisions, and final content approval with a human.

## Human review gates

Do not cross the next gate without confirmation:

1. **Brief:** learners, problem, result, and boundary are valid;
2. **Experience map:** core content comes from the instructor or clearly labeled external sources;
3. **Outline:** order, duration, module outputs, and scope are correct;
4. **Sample/manual:** tone, cases, exercises, and delivery requirements are correct;
5. **Final text:** the approved text matches the version used for slides, documents, or publishing;
6. **Retrospective:** facts and inferences are separated before becoming a reusable rule.

## Output protocol

Default to a reviewable Markdown deliverable in the user's requested location. If no location is specified, use the current workspace when file creation is available; otherwise return the structured draft in the conversation.

Do not overwrite an existing final version. Read it first and create an adjacent version or incremental update. If the intake gate is not met, create only an intake brief.

The main deliverable should include:

- course brief;
- positioning and observable result;
- learner and problem definition;
- content boundary;
- course structure;
- module or lesson actions and outputs;
- instructor cases and evidence;
- AI-use boundary;
- human review gates;
- delivery, feedback, retrospective, and assetization;
- assumptions still requiring verification.

## Quality check

- [ ] Actual learners and repeated problems are clear.
- [ ] The end result is observable, submittable, and reviewable.
- [ ] Every lesson or module has an action and an artifact.
- [ ] Core content comes from instructor experience or labeled external material.
- [ ] No invented cases, statistics, testimonials, promises, or tool effects.
- [ ] Sequence follows learning dependency.
- [ ] Cases precede practice, and practice receives feedback.
- [ ] Duration, difficulty, and workload fit the constraints.
- [ ] Links, tools, accounts, and source materials are minimally verified.
- [ ] Personal, learner, client, and confidential information is anonymized or authorized.
- [ ] Final text is approved before visual production or publishing.
- [ ] Retrospective and asset location are defined.

Report what materials were read, the course format, learner result, files produced, confirmed judgments, unresolved assumptions, the next human review gate, and whether the work has entered slide, document, or publishing production. Do not call a draft course text a completed course.
